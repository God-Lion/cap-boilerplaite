# ADR-004: i18n Strategy

Status: Accepted | Date: 2026-03-23

## Context
CAP Boilerplate supports global customers and must provide consistent multi-language support (English, Arabic, French) with RTL handling. The implementation must be scalable across modules and align with existing module boundaries.

## Decision
Use `i18next` as the central localization engine with per-module dictionary files under `src/data/dictionaries/{en,ar,fr}.json`.

- Each package/module maintains its own dictionaries for feature isolation.
- Use keyspaced translation keys like `auth.signin.title`.
- Container app (`app`) configures i18next provider and locale detection.
- Each module exposes `useTranslation` wrapper (`@cap/*/hooks/useI18n` optional) to enforce consistency.

## Alternatives Considered
1. Centralized global dictionary in `platform-core`: rejected due to poor modularity and harder release isolation.
2. Using `formatjs`/`react-intl`: rejected due to existing project standard on `i18next`, and smoother migration path.

## Consequences
- Positive: modular translations, minimal cross-module coupling, good support for RTL via `i18next` language detector.
- Positive: ability to ship module-specific dictionary updates independently.
- Negative: requires discipline for key names and duplicate detection.

## Implementation details
- All translation files live at:
  - `packages/modules/auth/src/data/dictionaries/en.json`
  - `packages/modules/auth/src/data/dictionaries/ar.json`
  - `packages/modules/auth/src/data/dictionaries/fr.json`
- Update `app/src/Providers.tsx` to initialize i18next with namespaces for each module.
- Ensure UI toggles (language switcher) persist in local storage and set class `dir` attribute for RTL.
- Add lint script to check missing translation keys as part of CI.
